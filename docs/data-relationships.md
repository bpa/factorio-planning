# Data Relationships

## Items And Recipes

Recipe prototypes are the production graph. A recipe has a name, category/categories, ingredients, one or more results, and `energy_required`. Ingredients point to item or fluid inputs; results point to produced items or fluids. An item can have multiple recipes, and one recipe can produce multiple results. Keep recipe identity and output quantities so a multi-output recipe is not mistaken for one independent machine per item. Select one applicable recipe per planned product; never union inputs from mutually exclusive alternatives. When one selected recipe serves several product targets through co-products, count its machines once and check that shared machine count against all target rates, allowing for surplus.

Item prototypes add metadata such as `subgroup`; use that to classify intermediate products and as a modest suggestion signal. Subgroup is not a recipe-eligibility rule. The current reader builds item nodes from recipe inputs and outputs, but does not read item prototypes or retain subgroup.

## Technology And Availability

Many recipe prototypes start with `enabled = false` and become available through a technology `unlock-recipe` effect. In the installed Base data, for example, early technologies carry these unlock effects. Therefore the startup boolean alone does not distinguish ordinary research-gated content from unavailable content. For a planner covering normal progression, derive effective availability from either `enabled = true` or at least one technology unlock, then verify a valid production path. The official API defines recipe `hidden` as hiding the recipe from crafting menus and other recipe-selection lists; item `hidden` suppresses the item from lists such as logistics requests and filters. Neither field means “unavailable in normal play.” Keep visibility policy separate from gameplay availability. A save-specific “already researched” mode would need research-state input beyond the current static data.

Construct the normal-play candidate set from outputs of start-enabled recipes and recipes unlocked by technology, with compatible production methods. Do not treat every parsed item or entity prototype as an unlockable. For placeable entity goals, trace the entity to its placeable item and require a normal acquisition or unlock path for that item. In the installed Base data, `infinity-chest` is a hidden `infinity-container` prototype, but there is no corresponding recipe or technology unlock; exclude it for lacking a normal progression path, not merely because it is hidden.

The recipe flag `hide_from_player_crafting` is narrower: the API says it hides a recipe from the player's crafting screen while leaving it available for machine selection. In the installed Base data, `rocket-part` has this flag and is machine-made. Technologies also have prerequisites and research costs, which the separate technology planner already models. The crafting page only needs unlock relationships for recipe eligibility and optional availability context; it need not duplicate science-cost calculations.

## Recipes And Machines

An assembling machine is compatible with a recipe when one of the machine's `crafting_categories` matches a recipe's `categories` entry. The installed Base recipe prototypes use the plural `categories` field. Category match is necessary but not sufficient: recipe fluid inputs/outputs must also match the machine's fluid-box capabilities. The entity's `crafting_speed` scales recipe time, which is specified at speed 1. For a recipe requiring $E$ seconds and a machine speed $S$, base time per craft is $E / S$ seconds; machine crafts per second are $S / E$. Output quantity scales item production rate. For a chosen target rate, machine count can then be estimated by rounding the required producer count up.

Use the entity's `module_slots`, allowed effects, and collision box to describe machine options. The requested integer footprint is `ceil(max - min)` on each collision-box axis. This is a planning estimate, not a complete tile-placement solver; orientation, adjacency, belts, pipes, and beacon placement can add constraints. The user-requested assembling-machine reader is not sufficient for every recipe category: smelting, oil processing, chemistry, centrifuging, and other categories require their corresponding production-machine families.

## Modules And Beacons

Modules can alter speed, productivity, energy consumption, and (in Space Age) quality. Quality is out of scope here. Read the selected machine's allowed effects and slots, and the module prototype effects; do not infer productivity eligibility solely from an item's subgroup. Recipe-level `allow_productivity` permission is the direct constraint for productivity-module estimates.

Beacons transmit module effects to eligible nearby machines. Beacon layout, effect transmission, and the number of affected machines influence the result, so a first version should present explicit module/beacon presets and label estimates rather than pretend to optimize layouts. Factorio's wiki describes beacons as covering a 9x9 area and allowing speed/efficiency modules but not productivity/quality modules; prototype fields should remain authoritative for the selected game data.

## Mall Inputs And Outputs

For a mall, compute its external input set from the inputs of selected recipes after subtracting only outputs generated inside that same mall. Outputs from another mall do not remove or discount an input connection. Any item is a valid input regardless of whether another mall produces it; show the producing mall(s) and their output rates as supplier information. Its connection budget is the count of distinct external input material types plus distinct product types the mall exposes as outputs. Count a type once in each direction if it is both imported and exported; quantities do not affect the count. Cargo items and fluids each consume one connection, with no separate fluid weighting or allowance. Credit co-products from a selected recipe once against every matching target, rather than counting a separate producer for each output. Factorio distinguishes machine production from hand crafting: recipes involving fluids cannot be manually crafted, and assembling machine 1 cannot process fluid recipes. Production machines also do not automatically chain-craft missing intermediates, so each dependency needs an explicit production source or an available input.

For each configured production line, estimate a steady-state rate for each product as `machine count × expected output units per craft × effective crafting speed / energy_required × 60`. Expected output includes selected productivity effects; effective speed includes supported machine/module/beacon effects. Aggregate rates for each product across lines in a mall and recalculate them after any machine count, recipe, machine, module, or beacon change. Display line output rates prominently in the machine editor and the mall's aggregated product rates in an output-rate column in the mall list. These are production-rate annotations; they do not change whether an item is a valid input elsewhere.

The same product may be generated by multiple malls. List all such malls as suppliers with their rates; production in one mall does not make the item a different kind of input in another. Recommendations should weight shared external inputs most strongly, then compatible function/category and intermediate subgroup. Configured combined input/output limits inform fit and ranking; they do not prevent the player from choosing a product.

## Current Limits

The parser extracts static Lua tables and does not execute Lua functions, `require`, loops, or computed expressions. The current recipe reader ignores fluid entries, recipe availability/hidden flags, item subgroups, and most recipe variants. The technology payload drops recipe unlock effects, and no entity, module, or beacon payload is currently generated. See the [implementation plan](crafting-page-plan.md). Background: [Crafting](https://wiki.factorio.com/Crafting) and [Time](https://wiki.factorio.com/Time).
